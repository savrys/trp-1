# Bikely — сервис аренды велосипедов

## Назначение

Веб-приложение автоматизирует работу пункта проката велосипедов:
ведёт парк велосипедов и станции проката, хранит клиентов, регистрирует
аренду, показывает историю аренд и формирует статистику. Проект продолжает
предыдущие практические работы: HTML-шаблоны, маршруты и пользовательские
сценарии сохранены, а слой доступа к данным переведён с прямых SQL-запросов
(`sqlite3`) на **Django ORM** (ПР9).

## Технологии

- Python 3.12+;
- Django 5.2;
- SQLite (файл `db.sqlite3`);
- доступ к данным — через Django ORM (модели, менеджеры, `QuerySet`);
- Bootstrap 5 для оформления страниц.

## Страницы и пользовательские сценарии

| Адрес                  | Страница             | Возможности                                                              |
|------------------------|----------------------|--------------------------------------------------------------------------|
| `/`                    | Главная              | Станции с числом аренд, сводные показатели парка и аренд                 |
| `/bikes/`              | Каталог велосипедов  | Поиск по модели и типу, фильтр по типу и доступности, сортировка         |
| `/bikes/<id>/`         | Карточка велосипеда  | Характеристики велосипеда и история его аренды                           |
| `/rentals/`            | Список аренд         | Поиск, фильтры (статус, велосипед, клиент, станция), сортировка, пагинация |
| `/rentals/<id>/`       | Карточка аренды      | Данные аренды, количество аренд клиента, завершение аренды               |
| `/rentals/statistics/` | Статистика           | Агрегаты по станциям, клиентам и типам велосипедов                       |
| `/admin/`              | Админка Django       | Управление станциями, велосипедами, клиентами и арендами                |
| любой несуществующий адрес | Страница 404     | Оформленная страница «Страница не найдена» со ссылками на разделы       |

Сценарии:

1. Просмотр каталога, поиск нужной модели и фильтрация свободных велосипедов.
2. Просмотр карточки велосипеда вместе с историей аренды.
3. Просмотр списка аренд с фильтрами по связанным объектам и постраничным выводом.
4. Завершение активной аренды: велосипед автоматически возвращается в парк.
5. Просмотр статистики по станциям, клиентам и типам велосипедов.

## Модели данных

| Модель    | Приложение     | Поля                                                                   |
|-----------|----------------|------------------------------------------------------------------------|
| `Station` | `web_bikes`    | `name`, `capacity`                                                     |
| `Bike`    | `web_bikes`    | `model`, `type` (TextChoices), `is_available`                          |
| `User`    | `web_rentals`  | `name`, `email` (уникальный)                                           |
| `Rental`  | `web_rentals`  | `bike`, `user`, `station`, `start_time`, `is_completed`                |

### Модель `Station`

Станция проката: название и вместимость. Сортировка по названию.

### Модель `Bike`

Велосипед парка. Тип задан через `Bike.Type` (`TextChoices`):
`Mountain` — горный, `Touring` — туристический, `Urban` — городской,
`Child` — детский. Поле `is_available` показывает, свободен ли велосипед.

### Модель `User`

Клиент сервиса: имя и электронная почта (поле `email` уникально).

### Модель `Rental`

Факт аренды велосипеда клиентом на станции. Три внешних ключа
(`ForeignKey`) с `related_name="rentals"` и политикой `on_delete=PROTECT`:
удаление велосипеда, клиента или станции, у которых есть аренды, запрещено.

Дополнительно у модели есть:

- свойство `is_active` — аренда не завершена;
- метод `complete()` — помечает аренду завершённой и возвращает велосипед
  в парк (`Bike.objects.filter(...).update(is_available=True)`).

### Связи между моделями

```
Bike   1 ──── N Rental
User   1 ──── N Rental
Station 1 ─── N Rental
```

Обратные связи доступны как `bike.rentals`, `user.rentals`, `station.rentals`,
поэтому представления используют `select_related()` и `annotate(Count("rentals"))`
вместо ручных `JOIN`-запросов.

## Операции Django ORM в проекте

- `Bike.objects.filter(...)`, `exclude(...)`, `order_by(...)` — каталог велосипедов;
- `Q(model__icontains=...) | Q(type__icontains=...)` — поиск по нескольким полям;
- `Rental.objects.select_related("bike", "user", "station")` — список аренд без
  лишних запросов;
- `Count(..., filter=Q(...))`, `Avg()`, `Max()` — агрегаты на страницах аренд
  и статистики;
- `values("type").annotate(...)` — группировка велосипедов по типу;
- `Bike.objects.filter(pk=...).update(is_available=True)` — возврат велосипеда
  в парк при завершении аренды;
- `Paginator` — постраничный вывод списка аренд с сохранением фильтров.

## Миграции

Миграции приложений хранятся в репозитории:

- `web_bikes/migrations/0001_initial.py` — модели `Station` и `Bike`;
- `web_rentals/migrations/0001_initial.py` — модели `User` и `Rental`.

Создание и применение миграций:

```bash
python manage.py makemigrations
python manage.py migrate
```

Проверить, что модели и миграции согласованы:

```bash
python manage.py makemigrations --check --dry-run
```

## Запуск проекта

1. Клонируйте репозиторий:

   ```bash
   git clone <адрес репозитория>
   cd trp-1
   ```

2. Создайте и активируйте виртуальное окружение:

   ```bash
   python -m venv venv
   venv\Scripts\activate
   ```

   В Linux/macOS: `source venv/bin/activate`.

3. Установите зависимости:

   ```bash
   pip install -r requirements.txt
   ```

4. Примените миграции (создадут таблицы `web_bikes_station`,
   `web_bikes_bike`, `web_rentals_user`, `web_rentals_rental`):

   ```bash
   python manage.py migrate
   ```

5. Наполните базу данными (см. следующий раздел).

6. Создайте суперпользователя для доступа к админке:

   ```bash
   python manage.py createsuperuser
   ```

7. Запустите сервер разработки:

   ```bash
   python manage.py runserver
   ```

8. Откройте в браузере `http://127.0.0.1:8000/`,
   админка — `http://127.0.0.1:8000/admin/`.

## Наполнение базы данных

### Перенос данных из базы ПР7

Скрипт `db/import_sqlite_to_orm.py` читает таблицы `bikes`, `users`, `stations`
и `rentals` из `data/bikely.sqlite` и сохраняет записи через Django ORM,
сохраняя исходные идентификаторы. Запускать после `python manage.py migrate`:

```bash
python db/import_sqlite_to_orm.py
```

### Fixtures

Выгрузка текущих данных в fixture-файл и загрузка его в другую базу:

```bash
python manage.py dumpdata web_bikes web_rentals --indent 2 --output db/fixtures/bikely.json
python manage.py loaddata db/fixtures/bikely.json
```

Готовый файл `db/fixtures/bikely.json` уже находится в репозитории.
Fixture должен быть в кодировке UTF-8: на Windows перед выгрузкой
удобно выполнить `set PYTHONUTF8=1` (PowerShell: `$env:PYTHONUTF8='1'`),
поскольку перенаправление вывода `>` в PowerShell создаёт UTF-16.

Fixtures не создают таблицы: сначала выполняются миграции, затем `loaddata`.
Если файл базы `db.sqlite3` отсутствует, база создаётся миграциями, а данные
переносятся скриптом импорта или через fixture.

## Обработка ошибки 404

Страница `templates/404.html` наследует `base.html`, поэтому у неё есть меню,
подвал и ссылки на основные разделы сайта.

- при `DEBUG = False` используется обработчик
  `handler404 = "web_main.views.page_not_found"` (файл `bikely/urls.py`);
- при `DEBUG = True` Django показывает техническую страницу с отладочной
  информацией, поэтому `bikely.middleware.Custom404Middleware` заменяет ответ
  404 на шаблон `404.html`; адреса `/admin/` и `/static/` исключены.

Проверить страницу можно, открыв любой несуществующий адрес, например
`http://127.0.0.1:8000/no-such-page/`.
