# Bikely — сервис аренды велосипедов

## Назначение

Веб-приложение автоматизирует работу пункта проката велосипедов:
ведёт парк велосипедов и станции проката, хранит клиентов, регистрирует
аренду, показывает историю аренд и формирует статистику. Проект продолжает
предыдущие практические работы: HTML-шаблоны и маршруты сохранены, данные
обрабатываются через **Django ORM**, а в ПР10 добавлены административная
панель, пользовательские менеджеры и `QuerySet`, автоматические slug,
генерируемое поле, статусы аренды, контекстный процессор и Django Debug
Toolbar.

## Технологии

- Python 3.12+;
- Django 5.2;
- SQLite (файл `db.sqlite3`);
- доступ к данным — через Django ORM (модели, менеджеры, `QuerySet`);
- Django Debug Toolbar 8 (только для локальной отладки);
- `Unidecode` для транслитерации названий велосипедов в slug;
- Bootstrap 5 для оформления страниц.

## Страницы и пользовательские сценарии

| Адрес                  | Страница             | Возможности                                                              |
|------------------------|----------------------|--------------------------------------------------------------------------|
| `/`                    | Главная              | Станции с числом аренд, сводные показатели парка и аренд                 |
| `/bikes/`              | Каталог велосипедов  | Поиск по модели и типу, фильтр по типу и доступности, сортировка         |
| `/bikes/<slug>/`       | Карточка велосипеда  | Характеристики велосипеда и история его аренды                           |
| `/rentals/`            | Список аренд         | Поиск, фильтры (статус, велосипед, клиент, станция), сортировка, пагинация |
| `/rentals/<id>/`       | Карточка аренды      | Данные аренды, количество аренд клиента, завершение аренды               |
| `/rentals/statistics/` | Статистика           | Агрегаты по станциям, клиентам и типам велосипедов                       |
| `/admin/`              | Админка Django       | Управление станциями, велосипедами, клиентами и арендами                |
| любой несуществующий адрес | Страница 404     | Оформленная страница «Страница не найдена» со ссылками на разделы       |

Сценарии:

1. Просмотр каталога, поиск нужной модели и фильтрация свободных велосипедов.
2. Просмотр карточки велосипеда вместе с историей аренды.
3. Просмотр списка аренд с фильтрами по связанным объектам и постраничным выводом.
4. Завершение активной аренды: велосипед автоматически возвращается в парк.
5. Просмотр статистики по станциям, клиентам и типам велосипедов.
6. Управление данными в админке: встроенные аренды в карточках, фильтры,
   поиск, автодополнение связанных полей и массовые действия со статусами.

## Модели данных

| Модель    | Приложение     | Поля                                                                   |
|-----------|----------------|------------------------------------------------------------------------|
| `Station` | `web_bikes`    | `name`, `capacity`, `is_large` (генерируемое)                          |
| `Bike`    | `web_bikes`    | `model`, `type` (TextChoices), `is_available`, `slug`                  |
| `User`    | `web_rentals`  | `name`, `email` (уникальный)                                           |
| `Rental`  | `web_rentals`  | `bike`, `user`, `station`, `start_time`, `status` (TextChoices)        |

### Модель `Station`

Станция проката: название и вместимость. Сортировка по названию. Поле
`is_large` объявлено как `GeneratedField` с `db_persist=True`: СУБД сама
вычисляет признак «крупная станция» (вместимость от 20 мест) и обновляет
его при изменении `capacity`. Поле доступно только для чтения в админке
и не задаётся вручную.

### Модель `Bike`

Велосипед парка. Тип задан через `Bike.Type` (`TextChoices`):
`Mountain` — горный, `Touring` — туристический, `Urban` — городской,
`Child` — детский. Поле `is_available` показывает, свободен ли велосипед.

Поле `slug` уникально и заполняется автоматически при первом сохранении:
название транслитерируется через `Unidecode`, очищается `slugify`, после
чего добавляется первичный ключ (`format-1411-1`). При повторном сохранении
slug не меняется, поэтому ссылка на карточку остаётся стабильной. Метод
`get_absolute_url()` строит адрес `/bikes/<slug>/`.

Пользовательский `BikeQuerySet` предоставляет методы `available()`,
`available_on(day)` и `with_rental_stats()`; последний аннотирует каждый
велосипед количеством всех и активных аренд без запросов в цикле.

### Модель `User`

Клиент сервиса: имя и электронная почта (поле `email` уникально).
`UserQuerySet.with_rental_stats()` добавляет `rentals_total` и
`rentals_active`, которые используются в админке и статистике.

### Модель `Rental`

Факт аренды велосипеда клиентом на станции. Три внешних ключа
(`ForeignKey`) с `related_name="rentals"` и политикой `on_delete=PROTECT`:
удаление велосипеда, клиента или станции, у которых есть аренды, запрещено.

Статус задан через `Rental.Status` (`TextChoices`):

- `active` — «Активна» (значение по умолчанию);
- `completed` — «Завершена»;
- `cancelled` — «Отменена».

Для поля статуса создан индекс, а также составной индекс
`status + -start_time`. Дополнительно у модели есть:

- свойство `is_active` — аренда имеет статус `active`;
- метод `complete()` — переводит активную аренду в `completed`
  и возвращает велосипед в парк;
- метод `cancel()` — переводит активную аренду в `cancelled`
  и также освобождает велосипед;
- методы `complete()`/`cancel()` идемпотентны: для аренды с другим статусом
  они возвращают `False` и не меняют данные.

`RentalQuerySet` содержит методы `active()`, `completed()`, `cancelled()`,
`with_related()`, `for_bike()`, `for_user()`, `for_station()`,
`in_period()` и `statistics()`. Метод `statistics()` одним SQL-запросом
возвращает общее число аренд, количество аренд по каждому статусу и время
последнего начала аренды.

### Связи между моделями

```
Bike   1 ──── N Rental
User   1 ──── N Rental
Station 1 ─── N Rental
```

Обратные связи доступны как `bike.rentals`, `user.rentals`, `station.rentals`,
поэтому представления используют `select_related()` и
`annotate(Count("rentals"))` вместо ручных `JOIN`-запросов. Аннотации
`with_rental_stats()` дают каждой станции, клиенту и велосипеду поля
`rentals_total` и `rentals_active` без N+1-запросов.

## Операции Django ORM в проекте

- `Bike.objects.filter(...)`, `exclude(...)`, `order_by(...)` — каталог велосипедов;
- `Q(model__icontains=...) | Q(type__icontains=...)` — поиск по нескольким полям;
- `Rental.objects.with_related()` (`select_related`) — список аренд без
  лишних запросов;
- `Rental.objects.active()`, `completed()`, `cancelled()` — фильтрация по
  статусу через пользовательский `QuerySet`;
- `Rental.objects.statistics()` — агрегаты по статусам и время последней
  аренды одним запросом;
- `Station.objects.with_rental_stats()`, `Bike.objects.with_rental_stats()`,
  `User.objects.with_rental_stats()` — количество всех и активных аренд;
- `Count(..., filter=Q(...))`, `Avg()`, `Max()` — агрегаты на страницах аренд
  и статистики;
- `values("type").annotate(...)` — группировка велосипедов по типу;
- `Bike.objects.filter(pk=...).update(is_available=True)` — возврат велосипеда
  в парк при завершении или отмене аренды;
- `Paginator` — постраничный вывод списка аренд с сохранением фильтров.

## Административная панель

Все модели зарегистрированы в `django.contrib.admin`:

- заголовки панели настраиваются в `web_main/admin.py`;
- в карточках велосипеда, станции и клиента показаны встроенные аренды
  (`TabularInline`);
- списки поддерживают поиск, фильтры, сортировку, `list_editable`,
  `date_hierarchy`, `save_on_top` и постраничный вывод;
- связанные поля используют `autocomplete_fields`, поэтому для моделей
  заданы `search_fields`;
- списки вызывают `with_rental_stats()`, а аренды — `with_related()`,
  что исключает N+1-запросы;
- у аренд есть массовые действия «Завершить», «Отменить» и «Вернуть
  в работу»; действия меняют статус и доступность велосипеда;
- у велосипеда настроен переход `view_on_site` на публичную страницу
  по slug.

## Django Debug Toolbar

Панель подключается в `bikely/settings.py` только при `DEBUG = True`,
установленном пакете и запуске не в режиме тестов. Маршрут `/__debug__/`
добавляется в `bikely/urls.py` при тех же условиях. Функция
`bikely.debug.show_toolbar` показывает панель только для хостов
`127.0.0.1` и `localhost`; `INTERNAL_IPS` содержит те же адреса.
Во время `manage.py test` приложение и middleware панели не
подключаются, поэтому тестовый клиент не получает отладочную панель.

## Миграции

Миграции приложений хранятся в репозитории:

- `web_bikes/migrations/0001_initial.py` — модели `Station` и `Bike`;
- `web_bikes/migrations/0002_station_is_large.py` — генерируемое поле
  `Station.is_large`;
- `web_bikes/migrations/0003_bike_slug.py` — добавление поля `Bike.slug`;
- `web_bikes/migrations/0004_populate_bike_slugs.py` — заполнение slug
  существующих велосипедов;
- `web_bikes/migrations/0005_alter_bike_slug.py` — уникальность и параметры
  `Bike.slug`;
- `web_bikes/migrations/0006_...` — согласование метаданных полей модели;
- `web_rentals/migrations/0001_initial.py` — модели `User` и `Rental`;
- `web_rentals/migrations/0002_rental_status.py` — новое поле `Rental.status`;
- `web_rentals/migrations/0003_migrate_rental_statuses.py` — перенос значений
  `is_completed` в статусы (с обратной операцией);
- `web_rentals/migrations/0004_remove_rental_is_completed.py` — удаление
  устаревшего логического поля;
- `web_rentals/migrations/0005_...` — согласование метаданных полей модели.

Миграции `0004_populate_bike_slugs` и `0003_migrate_rental_statuses`
являются data-миграциями: они приводят существующие записи к новой схеме
без потери данных.

Создание и применение миграций:

```bash
python manage.py makemigrations
python manage.py migrate
```

Проверить, что модели и миграции согласованы:

```bash
python manage.py makemigrations --check --dry-run
```

## Запуск проекта

1. Клонируйте репозиторий:

   ```bash
   git clone <адрес репозитория>
   cd trp-1
   ```

2. Создайте и активируйте виртуальное окружение:

   ```bash
   python -m venv venv
   venv\Scripts\activate
   ```

   В Linux/macOS: `source venv/bin/activate`.

3. Установите зависимости:

   ```bash
   pip install -r requirements.txt
   ```

4. Примените миграции (создадут таблицы `web_bikes_station`,
   `web_bikes_bike`, `web_rentals_user`, `web_rentals_rental`):

   ```bash
   python manage.py migrate
   ```

5. Наполните базу данными (см. следующий раздел).

6. Создайте суперпользователя для доступа к админке:

   ```bash
   python manage.py createsuperuser
   ```

7. Запустите сервер разработки:

   ```bash
   python manage.py runserver
   ```

8. Откройте в браузере `http://127.0.0.1:8000/`,
   админка — `http://127.0.0.1:8000/admin/`.

## Наполнение базы данных

### Перенос данных из базы ПР7

Скрипт `db/import_sqlite_to_orm.py` читает таблицы `bikes`, `users`, `stations`
и `rentals` из `data/bikely.sqlite` и сохраняет записи через Django ORM,
сохраняя исходные идентификаторы. Логическое поле `is_completed` исходной
базы преобразуется в `Rental.Status` (`completed` или `active`), а slug
велосипедов создаётся автоматически при сохранении модели. Запускать после
`python manage.py migrate`:

```bash
python db/import_sqlite_to_orm.py
```

### Fixtures

Выгрузка текущих данных в fixture-файл и загрузка его в другую базу:

```bash
# Windows PowerShell: включить UTF-8 перед выгрузкой.
$env:PYTHONUTF8='1'
python manage.py dumpdata web_bikes web_rentals --indent 2 --output db/fixtures/bikely.json
python manage.py loaddata db/fixtures/bikely.json
```

Для cmd.exe используется `set PYTHONUTF8=1`. Без этой настройки Python на
Windows может записать файл в кодировке системы (cp1251), и `loaddata`
не сможет его прочитать. Готовый файл `db/fixtures/bikely.json` уже
находится в репозитории и содержит актуальные `slug` велосипедов
и статусы аренд.

Fixtures не создают таблицы: сначала выполняются миграции, затем `loaddata`.
Если файл базы `db.sqlite3` отсутствует, база создаётся миграциями, а данные
переносятся скриптом импорта или через fixture.

## Обработка ошибки 404

Страница `templates/404.html` наследует `base.html`, поэтому у неё есть меню,
подвал и ссылки на основные разделы сайта.

- при `DEBUG = False` используется обработчик
  `handler404 = "web_main.views.page_not_found"` (файл `bikely/urls.py`);
- при `DEBUG = True` Django показывает техническую страницу с отладочной
  информацией, поэтому `bikely.middleware.Custom404Middleware` заменяет ответ
  404 на шаблон `404.html`; адреса `/admin/` и `/static/` исключены.

Проверить страницу можно, открыв любой несуществующий адрес, например
`http://127.0.0.1:8000/no-such-page/`.
